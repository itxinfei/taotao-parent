```

技术栈：Spring 4.2 + Spring MVC + MyBatis + Dubbo + ZooKeeper +
        Redis + Solr + ActiveMQ + FastDFS + FreeMarker + Quartz

项目描述：
    基于 Dubbo + ZooKeeper 的分布式 B2C 电商系统，包含后台管理、门户、
    搜索、购物车、订单、单点登录等 12 个独立模块，覆盖电商完整业务闭环。

核心职责与亮点：
    ▸ 服务治理：负责 Dubbo 服务拆分与注册中心搭建，5 个 Service + 7 个 Web
      模块通过 ZooKeeper 完成服务注册与发现，实现模块间解耦与独立部署；
    ▸ 缓存设计：商品详情采用 Redis 缓存（Cache-Aside 模式），命中率显著
      提升，并处理了缓存穿透、一致性等经典问题；
    ▸ 异步解耦：商品上架后通过 ActiveMQ 主题消息驱动 Solr 索引同步与
      FreeMarker 页面静态化，上架到搜索可见控制在秒级；
    ▸ 分布式 ID：使用 Redis incr 原子自增生成全局唯一订单号，替代数据库
      自增，解决分布式场景下 ID 冲突问题；
    ▸ 单点登录：基于 Token + Redis 实现跨模块登录态共享，支持 JSONP 跨域。
```

### 2.1 万能开场模板

> "我做的项目是一个基于 **Dubbo + ZooKeeper** 的分布式电商平台 —— 淘淘商城。
> 整个系统包含后台管理、门户、搜索、购物车、订单、单点登录 6 大业务域，
> 拆分成 12 个独立部署的模块。
>
> 我主要负责两块：
> **一是商品模块** —— 包括商品 CRUD、Redis 缓存、以及通过 ActiveMQ 消息
> 驱动 Solr 索引同步和页面静态化；
> **二是搜索模块** —— Solr 全文检索、高亮、分页。
>
> 项目中我重点解决了三个问题：
> 1）**分布式服务调用**：用 Dubbo + ZooKeeper 做服务注册与发现；
> 2）**缓存与一致性**：Cache-Aside 缓存 + 更新时删缓存 + 消息驱动最终一致；
> 3）**分布式 ID**：Redis incr 生成订单号。"

### 2.2 三个"必讲"亮点话术

| 亮点 | 一句话话术 |
|------|-----------|
| 缓存 | "商品详情先查 Redis，命中率约 XX%，未命中再查库并回填，更新时主动删缓存保证一致性" |
| 异步 | "商品上架后写库和发消息分离，Solr 索引与静态页生成异步完成，用户无感知等待" |
| 服务化 | "12 个模块通过 Dubbo 解耦，每个模块可独立开发、独立部署、独立扩容" |

## 3. 答辩常见问题预测（含答题思路）

### 3.1 架构类

**Q：为什么用 Dubbo 而不是直接 HTTP 调用？**
A：Dubbo 是 RPC 框架，相比 HTTP 调用：① 性能更高（长连接 + 二进制序列化）；
② 自带注册中心、负载均衡、超时重试等治理能力；③ 接口即契约，天然适合内部服务调用。

**Q：服务挂了一个，你的系统会怎样？**
A：Dubbo 会通过 ZooKeeper 感知 Provider 下线并剔除，Consumer 自动切换到其他
Provider（负载均衡）；如果全部挂掉则调用失败，由全局异常处理器兜底返回友好提示。

### 3.2 缓存类

**Q：缓存和数据库不一致怎么办？**
A：采用 Cache-Aside 模式：读时先查缓存、未命中查库回填；写时先写库再删缓存，
下次读时重建。允许极短时间不一致（最终一致）。要求更高的场景可加延迟双删或消息补偿。

**Q：Redis 挂了怎么办？**
A：本项目所有 Redis 操作都做了 try-catch 容错，Redis 异常时降级为直接查数据库，
不影响主流程（体验下降但可用）。

### 3.3 消息类

**Q：MQ 消息丢了怎么办？**
A：生产端失败重试 + 消费者失败记录日志；更可靠的做法是本地消息表（先写库再写
消息表，同事务，定时扫描补发）。

**Q：消息重复消费？**
A：本项目搜索消费者重复添加同一 id 文档到 Solr，Solr 按 id 覆盖，天然幂等；
如果是插入型操作，用唯一索引或 Redis setnx 做幂等。

### 3.4 搜索类

**Q：Solr 和 MySQL 都能查，为什么用 Solr？**
A：Solr 用倒排索引，支持中文分词、相关性排序、高亮，毫秒级响应；
MySQL LIKE 全表扫描，数据量大时性能差且无分词。

### 3.5 综合类

**Q：如果让你重构这个项目，你会怎么改？**
A：① 引入 Spring Cloud Alibaba（Nacos + Sentinel + Seata）替换老版本 Dubbo，
解决服务治理与分布式事务；② 用 RocketMQ 事务消息替代 ActiveMQ 解决一致性问题；
③ 数据库分库分表；④ 引入 Docker/K8s 部署、链路追踪。

**Q：项目最大难点是什么？**
A：商品上架后搜索不到的问题 —— 排查发现是 MQ 消息未消费导致索引没同步，
最终通过"消费者重试 + 失败日志 + 定时补偿"解决。这个问题的价值在于让我真正理解了
分布式系统"最终一致性"的落地方式。

## 4. 答辩演示准备清单

### 4.1 演示环境检查

| 项目 | 检查点 |
|------|--------|
| 中间件 | MySQL/Redis/ZK/Solr/MQ/FastDFS 全部启动 |
| 服务 | 5 个 Service + 7 个 Web 全部就绪 |
| 数据 | 有可演示的商品、订单、用户数据 |
| 网络 | 端口可访问，浏览器无代理拦截 |
| 备用方案 | 准备截图/录屏，防止现场环境故障 |

### 4.2 演示流程脚本（5~8 分钟）

```
1. 架构总览（30 秒）：打开架构图，讲清 12 模块分层
2. 后台演示（1 分钟）：登录 → 商品列表 → 编辑商品
3. 缓存演示（1 分钟）：redis-cli monitor 实时观察缓存读写
4. 搜索演示（1 分钟）：搜索关键词 → 高亮结果
5. 上架联动（1 分钟）：新增商品 → Solr 出现 → 静态页生成
6. 购物车/下单（1 分钟）：加购 → 下单 → 订单号生成
7. 单点登录（1 分钟）：登录 → 其他模块免登录
8. 总结（30 秒）：技术亮点 + 收获
```

### 4.3 演示中要"秀"的技术点

- `redis-cli monitor`：展示缓存穿透过程（第一次查库、之后命中缓存）
- ZooKeeper `ls /dubbo`：展示服务注册
- Solr 管理台：展示索引文档
- 后台修改商品 → 立刻刷新详情页：展示缓存一致性处理

```
"我先说结论：缓存穿透是指查询一个不存在的数据……
（原理）因为缓存没有这个 key，每次都打到数据库……
（项目）在淘淘商城，商品查询就是这样，我们通过缓存空值解决……
```
