## 1. 功能一：商品秒杀（核心难点）

### 1.1 需求分析

- 某商品限时限量抢购（如 100 件）
- 高并发：瞬间大量请求
- 要求：**不超卖**、**不压垮数据库**

### 1.2 架构思路（经典三段式）

```
浏览器（按钮置灰 + 简单限流）
   │
   ▼
Nginx（IP 限流 + 静态化秒杀页）
   │
   ▼
秒杀服务
   ├── Redis 预减库存（decr 原子操作，先拦截大部分请求）
   ├── 资格校验（一人一单：Redis setnx）
   │
   ▼ 预减成功 → 发送 MQ（削峰）
   │
   ▼
MQ 消费者（异步下单）
   └── 数据库乐观锁扣减（最终兜底防超卖）
```

### 1.3 表设计

```sql
-- 秒杀商品表
CREATE TABLE tb_seckill (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  item_id BIGINT NOT NULL COMMENT '商品ID',

  stock INT NOT NULL COMMENT '秒杀库存',

-- 秒杀订单表
```

### 1.4 核心代码

**第一步：Redis 预热库存（秒杀开始前）**

```java
// 把数据库库存同步到 Redis
jedisClient.set("seckill:stock:" + seckillId, String.valueOf(stock));
```

**第二步：预减库存 + 一人一单校验**

```java
public TaotaoResult seckill(Long seckillId, Long userId) {
    // 1. 一人一单：Redis setnx 防重复抢购
    String buyKey = "seckill:buy:" + seckillId + ":" + userId;
    Long success = jedisClient.setnx(buyKey, "1");   // 需在 JedisClient 增加 setnx
    if (success == 0) {
        return TaotaoResult.build(400, "您已抢购过该商品");
    }
    // 2. 预减库存（原子操作）
    Long rest = jedisClient.decr("seckill:stock:" + seckillId);
    if (rest < 0) {
        // 库存不足，回滚购买标记
        jedisClient.del(buyKey);
        return TaotaoResult.build(400, "商品已抢光");
    }
    // 3. 预减成功 → 发 MQ 异步下单
    jmsTemplate.send(seckillDestination, new MessageCreator() {
        @Override
        public Message createMessage(Session session) throws JMSException {
            MapMessage msg = session.createMapMessage();
            msg.setLong("seckillId", seckillId);
            msg.setLong("userId", userId);
            return msg;
        }
    });
    return TaotaoResult.ok();
}
```

**第三步：MQ 消费者 + 数据库乐观锁兜底**

```java
public void onMessage(Message message) {
    // 异步创建订单
    // 数据库扣减（乐观锁防超卖）：
    // UPDATE tb_seckill SET stock = stock - 1
    //  WHERE id = ? AND stock > 0;
    // 影响行数为 0 → 说明库存已被抢完，丢弃该单
}
```

### 1.5 面试延伸

| 问题 | 答案要点 |
|------|----------|
| 为什么 Redis 预减？ | 把库存判断从数据库搬到内存，抗住高并发读 |
| 超卖怎么防？ | 三层：Redis decr 原子 → MQ 削峰 → 数据库乐观锁兜底 |
| 一人一单怎么保证？ | 数据库唯一索引 (user_id, item_id) + Redis setnx |
| 用户抢到了但没支付？ | 超时释放库存（见 2.2 订单超时） |

## 2. 功能二：订单超时自动取消

### 2.1 需求

用户下单未支付，15 分钟后自动取消并释放库存。

### 2.2 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 定时轮询（本项目现状） | Quartz 每 N 分钟扫描 | 简单 | 不精确、扫描开销 |
| 延迟消息 | MQ 延迟队列 | 精确 | 依赖 MQ 能力 |
| Redis 过期监听 | key 过期回调 | 简单 | 过期事件有延迟、可靠性一般 |
| 时间轮 | 内存时间轮 | 高性能 | 进程重启丢失 |

**本项目现状**：`OrderJob` 每 30 分钟扫描 `create_time < now-2天` 的未付款订单关闭。
教学改进：把阈值改小（如 15 分钟）+ 结合延迟消息更精确。

### 3.2 领券防超发

```java
// 防止超发：先检查总数，再扣减（Redis 原子扣减）
Long rest = jedisClient.decr("coupon:left:" + couponId);
if (rest < 0) {
    jedisClient.incr("coupon:left:" + couponId);  // 回滚
    return TaotaoResult.build(400, "优惠券已领完");
}
// 插入用户券记录（唯一索引兜底一人一张）
```

### 3.3 下单用券

```
1. 校验用户券状态=未使用
2. 校验金额 ≥ 满减门槛
3. 下单金额 = 实付 - 券面额
4. 下单成功后：用户券置为已使用（同一事务）
```

## 5. 功能五：购物车优化

### 5.1 现状与问题

本项目购物车存 **商品全量 JSON 快照**（TbItem 序列化到 Cookie/Redis）。

问题：
1. Cookie 有大小限制（4KB），商品多了放不下
2. 快照中的价格可能过期（商品改价后购物车显示旧价）
3. 未登录/登录合并逻辑简单（只补缺失，不合并数量）

### 5.2 优化方案

| 问题 | 优化 |
|------|------|
| Cookie 大小 | 只存 `itemId:num` 轻量结构，展示时实时查商品 |
| 价格过期 | 展示时实时查库/缓存，价格以最新为准 |
| 登录合并 | 登录时 Cookie 与 Redis 按 itemId 合并数量（取大或求和） |
| 库存校验 | 结算时校验库存充足 |

### 6.2 完整流程

```
1. 订单交易成功（status=5）→ 可评价
2. 提交评价 → 校验"该用户买过该商品"（防刷单）
3. 评价成功 → 订单 buyer_rate 置 1
4. 商品评价数/好评率 → Redis 缓存，定时落库
```
