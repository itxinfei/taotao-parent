# 06 数据库设计详解

> 学习目标：理解淘淘商城 11 张核心表的结构、字段含义与设计思想，学会从"业务需求"推导"表结构"。

## 1. 数据库概览

- 数据库名：`taotao`
- 字符集：`utf8`
- 引擎：全部 InnoDB（支持事务、行锁）
- 初始化脚本：`taotao.sql`（位于 docs/ 目录）

### 1.1 表清单

| 表 | 业务域 | 说明 |
|----|--------|------|
| tb_item | 商品 | 商品主表（标题/价格/库存/图片） |
| tb_item_desc | 商品 | 商品描述（富文本 HTML） |
| tb_item_cat | 商品 | 商品类目树 |
| tb_item_param | 商品 | 类目规格参数模板 |
| tb_item_param_item | 商品 | 商品规格参数实例 |
| tb_content | 内容 | 广告位/内容记录 |
| tb_content_category | 内容 | 内容分类树 |
| tb_user | 用户 | 账号信息 |
| tb_order | 订单 | 订单主表 |
| tb_order_item | 订单 | 订单商品明细 |
| tb_order_shipping | 订单 | 收货与物流信息 |

### 1.2 表关系总览（ER 概念）

```
tb_item_cat（类目树）
   │ 1:N（cid 指向叶子类目）
   ▼
tb_item（商品） ── 1:1 ──► tb_item_desc（描述，item_id 即商品id）
   │
   │ 1:N
   ▼
tb_item_param_item（商品规格实例，item_id）
   ▲
   │ item_cat_id（类目级模板）
tb_item_param（规格模板）

tb_content_category（分类树） ── 1:N ──► tb_content（内容）

tb_user ── 1:N ──► tb_order（user_id）
                        │ 1:N
                        ▼
                tb_order_item（order_id）
                        │ 1:1
                        ▼
                tb_order_shipping（order_id）
```

## 2. 商品域表详解

### 2.1 tb_item —— 商品主表

| 字段 | 类型 | 说明 | 设计要点 |
|------|------|------|----------|
| id | bigint | 商品ID（同时是商品编号） | 应用层生成（时间戳+随机数），非自增 |
| title | varchar(100) | 商品标题 | 搜索的主字段 |
| sell_point | varchar(500) | 商品卖点 | 列表页展示 |
| price | bigint | 价格，**单位：分** | ⚠️ 用整数存金额，避免浮点误差 |
| num | int | 库存数量 | |
| barcode | varchar(30) | 条形码 | |
| image | varchar(500) | 商品图片（多张逗号分隔） | 逗号分隔的字符串数组 |
| cid | bigint | 所属类目（叶子类目） | 指向 tb_item_cat.id |
| status | tinyint | 1正常/2下架/3删除 | 逻辑删除标志 |
| created / updated | datetime | 创建/更新时间 | 所有表统一设计 |

**教学要点**：

1. **金额用"分"存整数**：`price=36900` 表示 369.00 元。浮点运算有精度问题
   （0.1+0.2≠0.3），金融金额必须用整数/Decimal。
2. **ID 不用自增**：分布式环境下多库自增会冲突，改由应用层生成唯一 ID。
3. **图片逗号分隔**：`image="url1,url2,url3"`，取第一张 `split(",")[0]` 做列表缩略图。
4. **逻辑删除**：不物理删行，用 status=3 标记，保证历史数据可追溯。

### 2.2 tb_item_desc —— 商品描述表

| 字段 | 类型 | 说明 |
|------|------|------|
| item_id | bigint | 商品ID（主键） |
| item_desc | text | 商品描述（富文本 HTML） |
| created / updated | datetime | 时间戳 |

**设计要点**：
- 主键就是商品 ID（1:1 关系），无需额外自增 ID
- 描述是长文本，与主表分离 —— **"大字段拆分"**：列表查询（selectByExample）不用加载描述，
  详情页才用 `selectByExampleWithBLOBs` 加载，提升列表性能

### 2.3 tb_item_cat —— 商品类目表（树形结构）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 类目ID |
| parent_id | bigint | 父类目ID，0 表示一级类目 |
| name | varchar(50) | 类目名称 |
| status | int(1) | 1正常/2删除 |
| sort_order | int | 同级排序 |
| is_parent | tinyint(1) | 是否为父类目（有子节点） |
| created / updated | datetime | 时间戳 |

**教学要点**：
- **邻接表模型**：用 `parent_id` 指向父节点，是最简单、最常见的树形存储方式
  （相比左右值模型/路径枚举，邻接表增删简单、查询用递归）
- `is_parent` 冗余字段：树组件展开时无需实时 COUNT 子节点，直接读标志
- 索引 `(parent_id, status)`：按父查子 + 过滤状态

### 2.4 tb_item_param —— 规格参数模板（类目级）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| item_cat_id | bigint | 商品类目ID |
| param_data | text | 参数模板，JSON 格式 |
| created / updated | datetime | 时间戳 |

**param_data 示例（手机类目）**：

```json
[
  {"group": "主体", "params": ["品牌", "型号", "颜色", "上市年份"]},
  {"group": "网络", "params": ["4G网络制式", "3G网络制式", "2G网络制式"]},
  {"group": "存储", "params": ["机身内存", "储存卡类型"]}
]
```

> 意义：**同一类目的商品共用一套参数模板**，运营在后台给"类目"配置模板，
> 录入商品时按模板填具体值。

### 2.5 tb_item_param_item —— 商品规格参数实例

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| item_id | bigint | 商品ID |
| param_data | text | 该商品的具体参数值，JSON |
| created / updated | datetime | 时间戳 |

**param_data 示例（某具体商品）**：

```json
[
  {"group": "主体", "params": [{"k": "品牌", "v": "华为"}, {"k": "型号", "v": "Mate60"}]}
]
```

> 展示时由 `ItemParamItemServiceImpl` 把 JSON 解析渲染成 HTML 表格。

## 3. 内容域表详解

### 3.1 tb_content_category —— 内容分类树

结构与 tb_item_cat 完全同构（id / parent_id / name / status / sort_order / is_parent / created / updated）。
典型数据：`淘淘商城 → 首页 → 大广告` 三级分类。

### 3.2 tb_content —— 内容表（广告位）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| category_id | bigint | 内容类目ID（大广告=89） |
| title / sub_title / title_desc | varchar | 标题、子标题、标题描述 |
| url | varchar | 点击跳转链接 |
| pic / pic2 | varchar | 主图 / 副图 |
| content | text | 富文本内容 |
| created / updated | datetime | 时间戳 |

**教学要点**：
- 门户首页的轮播图就来自 `category_id=89`（大广告）的内容记录
- 图片、链接、富文本分离，前端按广告位组件取对应字段渲染

## 4. 用户域表详解

### 4.1 tb_user —— 用户表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | bigint | 自增 | 用户ID |
| username | varchar(50) | **UNIQUE** | 用户名 |
| password | varchar(32) | NOT NULL | 密码 MD5 摘要（32位十六进制） |
| phone | varchar(20) | **UNIQUE** | 手机号 |
| email | varchar(50) | **UNIQUE** | 邮箱 |
| created / updated | datetime | NOT NULL | 时间戳 |

**教学要点**：

1. **唯一约束保证业务规则**：注册时校验"用户名/手机/邮箱不重复"，数据库层也建了 UNIQUE KEY 兜底 —— 应用校验 + 数据库约束双重保障。
2. **MD5 摘要**：`e10adc3949ba59abbe56e057f20f883e` 是 "123456" 的 MD5。
   教学项目用 MD5 演示（无盐），生产建议 BCrypt 加盐。
3. 登录时 `MD5(明文密码) == 库中值` 比对。

## 5. 订单域表详解

### 5.1 tb_order —— 订单主表

| 字段 | 类型 | 说明 |
|------|------|------|
| order_id | varchar(50) | 订单ID（主键，String！） |
| payment | varchar(50) | 实付金额（字符串，精确到2位小数） |
| payment_type | int(2) | 1在线支付 / 2货到付款 |
| post_fee | varchar(50) | 邮费 |
| status | int(10) | 1未付款 2已付款 3未发货 4已发货 5交易成功 6交易关闭 |
| create_time / update_time | datetime | 创建/更新时间 |
| payment_time / consign_time / end_time / close_time | datetime | 各流转节点时间 |
| shipping_name / shipping_code | varchar | 物流公司 / 物流单号 |
| user_id | bigint | 用户ID |
| buyer_message / buyer_nick | varchar | 买家留言 / 昵称 |
| buyer_rate | int(2) | 是否已评价 |

**教学要点**：

1. **订单号是 String 且非自增**：由 Redis `incr` 生成（分布式全局唯一），
   电商订单号通常还带业务含义（日期/来源/渠道），用 varchar 更灵活。
2. **订单状态机 + 时间戳矩阵**：每个状态流转都有独立时间字段
   （付款时间、发货时间、完成时间、关闭时间），便于运营查询与对账。
3. **冗余买家昵称**：下单时快照 `buyer_nick`，用户改名不影响历史订单 —— **数据快照**思想。

### 5.2 tb_order_item —— 订单商品明细

| 字段 | 类型 | 说明 |
|------|------|------|
| id | varchar(20) | 明细ID（Redis incr 生成） |
| item_id | varchar(50) | 商品ID |
| order_id | varchar(50) | 订单ID（关联 tb_order） |
| num | int | 购买数量 |
| title | varchar(200) | **商品标题快照** |
| price | bigint | 商品单价（分） |
| total_fee | bigint | 小计金额（分） |
| pic_path | varchar(200) | 商品图片快照 |

**设计要点**：
- **商品信息快照**：订单明细存标题/价格/图片的**副本**，而非只存 item_id。
  因为商品后来可能改价、改名、下架，但已下的订单必须按购买时的信息展示。
  这是电商订单设计的核心原则：**交易数据不可变，必须快照**。

### 5.3 tb_order_shipping —— 收货与物流

| 字段 | 类型 | 说明 |
|------|------|------|
| order_id | varchar(50) | 订单ID（主键，1:1） |
| receiver_name / receiver_phone / receiver_mobile | varchar | 收货人姓名/电话/手机 |
| receiver_state / receiver_city / receiver_district | varchar | 省/市/区 |
| receiver_address | varchar(200) | 详细地址 |
| receiver_zip | varchar(6) | 邮编 |
| created / updated | datetime | 时间戳 |

> 收货信息同样是下单时快照，不随用户资料变更而变。

## 6. 设计思想总结

### 6.1 本项目贯彻的六大设计原则

| 原则 | 体现 |
|------|------|
| 金额用整数/字符串 | price 用"分"存 bigint；订单金额用字符串 |
| 大字段拆分 | 商品描述独立成表，列表查询不加载 |
| 逻辑删除 | status 字段标记，不物理删行 |
| 快照不可变 | 订单明细/收货/买家昵称均冗余快照 |
| 应用层生成 ID | 商品 ID、订单号不依赖数据库自增 |
| 冗余字段换性能 | is_parent 标志避免递归计数 |

### 6.2 面试高频题：订单表为什么拆三张？

```
tb_order          订单整体（谁买的、多少钱、什么状态）
tb_order_item     买了什么（商品快照 × N）
tb_order_shipping 送到哪（收货地址）
```

原因：
1. **一对多**：一个订单多个商品，明细拆开避免"一行塞多个商品"
2. **查询隔离**：订单列表只查主表；详情再查明细/收货；避免大行宽
3. **变更隔离**：物流信息更新不影响商品明细

### 6.3 面试高频题：为什么订单号不用自增？

1. 分布式多库自增会重复
2. 订单号要可读（可含日期/渠道），自增无意义
3. 防止竞对通过订单号推测销量（安全）
4. Redis incr 原子自增 + 业务前缀，是常见替代方案
