# 04 关键技术点原理与实践

> 学习目标：深入理解淘淘商城用到的每一类关键技术 —— 不仅会用，更要懂原理。

## 1. Dubbo 分布式服务框架

### 1.1 什么是 Dubbo

Dubbo 是阿里巴巴开源的**高性能 RPC 框架**，核心解决分布式环境下"服务如何被远程调用"的问题。

```
┌────────────┐    注册/订阅    ┌──────────────┐
│  Consumer  │◄──────────────►│  Registry    │  （ZooKeeper）
│  (Web模块)  │                │  (注册中心)   │
└─────┬──────┘                └──────┬───────┘
      │         invoke               │  register
      ▼                              ▼
┌────────────┐                ┌──────────────┐
│  Provider  │                │  Provider    │
│ (Service)  │                │  (Service)   │
└────────────┘                └──────────────┘
```

**角色说明**：

| 角色 | 本项目对应 | 职责 |
|------|-----------|------|
| Provider | 5 个 service 模块 | 实现接口，启动时向注册中心注册 |
| Consumer | 7 个 web 模块 | 启动时订阅服务，拿到地址后直连调用 |
| Registry | ZooKeeper | 服务注册、发现、通知（节点变化推送） |
| Monitor | 无 | 统计调用次数与耗时（本项目未启用） |

### 1.2 项目中的配置解读

Service 端（`applicationContext-service.xml`）：

```xml
<!-- 应用名：用于监控与依赖分析 -->
<dubbo:application name="taotao-manager"/>
<!-- 注册中心地址 -->
<dubbo:registry protocol="zookeeper" address="zookeeper://172.168.20.221:2181"/>
<!-- RPC 协议与端口 -->
<dubbo:protocol name="dubbo" port="20880"/>
<!-- 暴露服务：接口 + 实现类引用 -->
<dubbo:service interface="com.taotao.service.ItemService" ref="itemServiceImpl" timeout="30000"/>
```

Web 端（`springmvc.xml`）：

```xml
<dubbo:application name="taotao-manager-web"/>
<dubbo:registry protocol="zookeeper" address="zookeeper://172.168.20.221:2181"/>
<!-- 引用远程服务，本地注入使用 -->
<dubbo:reference interface="com.taotao.service.ItemService" id="itemService"/>
```

### 1.3 一次 Dubbo 调用的完整过程

```
1. Consumer 启动 → 订阅 ZooKeeper 中 /dubbo/com.taotao.service.ItemService/providers 节点
2. Provider 启动 → 向该节点写入自己的地址（dubbo://ip:20880/...）
3. ZK 通知 Consumer 有新的 Provider 地址
4. Consumer 按负载均衡策略（默认 random）选一个地址
5. Consumer 与 Provider 建立 TCP 长连接，序列化参数 → RPC 调用 → 反序列化结果
6. 定时重连：Provider 下线，ZK 通知 Consumer 剔除该地址
```

### 1.4 常见面试问题

| 问题 | 答案要点 |
|------|----------|
| Dubbo 默认负载均衡？ | random（随机），还有 roundrobin、leastactive、consistenthash |
| 超时怎么配？ | `<dubbo:service timeout="30000"/>` 或 reference 端配置 |
| 重试机制？ | 默认重试 2 次（cluster=failover）；幂等操作可重试，非幂等要小心 |
| 直连调试？ | `dubbo:reference url="dubbo://ip:port"` 绕过注册中心直连 |
| 序列化方式？ | 默认 hessian2，支持 json、java 等 |
| 服务降级/容错？ | mock、failfast、failsafe 等集群容错模式 |

## 2. ZooKeeper 注册中心

### 2.1 ZooKeeper 是什么

分布式协调服务：维护一个**树形节点结构**（类似文件系统），支持节点监听与通知。

```
/dubbo
├── com.taotao.service.ItemService
│   ├── providers     ← Provider 写入地址
│   ├── consumers     ← Consumer 写入地址
│   ├── configurators
│   └── routers
├── com.taotao.service.ItemCatService
│   └── ...
```

### 2.2 本项目用到 ZK 的什么能力

| 能力 | 场景 |
|------|------|
| 节点注册 | Provider 把服务地址写到 providers 节点（临时节点） |
| 节点监听 | Consumer 监听 providers 节点，地址变化实时感知 |
| 会话过期 | Provider 宕机，ZK 会话超时删除临时节点，自动下线 |

### 2.3 常用操作命令

```bash
zkCli.sh -server localhost:2181
ls /dubbo/com.taotao.service.ItemService/providers   # 查看服务提供者
get /dubbo/com.taotao.service.ItemService/providers/dubbo%3A%2F%2F...
stat /dubbo                                            # 节点信息
```

### 2.4 与 Redis 做注册中心的区别

| 对比 | ZooKeeper | Redis |
|------|-----------|-------|
| 数据模型 | 树形节点 | Key-Value |
| 通知机制 | 原生 Watch 监听 | 需轮询/发布订阅模拟 |
| 一致性 | ZAB 协议强一致 | 弱一致 |
| 适用 | 注册中心、配置中心、分布式锁 | 缓存、队列 |

> 结论：Dubbo 官方也支持 Redis 注册中心，但 ZK 更标准、更可靠，是生产主流选择。

## 3. Redis 缓存与分布式会话

### 3.1 Redis 在项目中的四大用途

| 用途 | 实现 | 数据示例 |
|------|------|----------|
| 热点缓存 | get/set + expire | `ITEM_INFO:{id}:BASE` → 商品 JSON |
| Hash 缓存 | hget/hset/hdel | `INDEX_CONTENT` → field:分类ID |
| 分布式 ID | incr | `ORDER_ID_GEN_KEY` → 订单号 |
| 会话共享 | set + expire | `USER_SESSION:{token}` → 用户 JSON |

### 3.2 缓存读写套路（Cache-Aside）

```
读：先查缓存 → 命中返回；未命中 → 查库 → 回填缓存 → 返回
写：先写库 → 删除缓存（下次读时重建）
```

**为什么更新时"删缓存"而不是"改缓存"？**
—— 改缓存要考虑数据格式一致性、并发写竞争；删除让缓存"下次读时重建"更简单可靠，
这是业界主流做法（旁路缓存）。

### 3.3 缓存常见问题与对策

| 问题 | 现象 | 对策 |
|------|------|------|
| 缓存穿透 | 查询不存在的 key，每次都打数据库 | 缓存空值；布隆过滤器（本项目未用） |
| 缓存雪崩 | 大量 key 同时过期，DB 被打爆 | 过期时间加随机值；多级缓存 |
| 缓存击穿 | 某个热点 key 过期瞬间大量请求 | 互斥锁重建缓存（本项目未用） |
| 缓存一致性 | 缓存与库不一致 | 先写库再删缓存；短暂不一致可接受（最终一致） |

> 本项目采用最朴素的"先写库再删缓存"，教学重点是理解套路本身。

### 3.4 为什么用 Redis 存 Session

传统 Servlet Session 存在单台 Tomcat 内存里，集群部署时用户可能被路由到另一台，Session 就丢了。
把 Session（或 Token）存 Redis：

- **共享**：所有 Web 模块读同一份
- **持久**：Tomcat 重启 Session 不丢
- **可控**：过期时间、主动失效（登出）都容易实现

### 3.5 Jedis 客户端与连接池

```xml
<bean id="jedisPool" class="redis.clients.jedis.JedisPool">
    <constructor-arg name="host" value="172.168.20.221"/>
    <constructor-arg name="port" value="6379"/>
</bean>
```

封装层 `JedisClient` 接口有单机（Pool）与集群（Cluster）两套实现，业务代码只依赖接口，
**切换实现不用改业务代码** —— 这是面向接口编程的体现。

## 4. Solr 全文搜索引擎

### 4.1 为什么不用 MySQL 的 LIKE

| 对比 | MySQL LIKE '%手机%' | Solr |
|------|---------------------|------|
| 性能 | 全表扫描，数据量大时极慢 | 倒排索引，毫秒级 |
| 分词 | 无（只能整串匹配） | 中文分词，能搜"华为手机"匹配"手机" |
| 相关性 | 无排序算法 | TF-IDF 相似度排序 |
| 高亮 | 需手工处理 | 原生高亮支持 |
| 扩展 | 单机瓶颈 | 分布式分片 |

### 4.2 倒排索引原理

正排：文档 → 词（遍历找词）
倒排：词 → 文档列表（查词直接定位）

```
"华为手机 5G 旗舰"   → 分词 → 华为 / 手机 / 5G / 旗舰
索引：华为 → [doc1, doc3]
      手机 → [doc1, doc2]
查询"手机" → 直接命中 doc1、doc2
```

### 4.3 项目中的 Solr 配置

`applicationContext-solr.xml`：

```xml
<bean id="httpSolrServer" class="org.apache.solr.client.solrj.impl.HttpSolrServer">
    <constructor-arg name="baseURL" value="http://172.168.20.221:8983/solr/collection1"/>
</bean>
```

### 4.4 三种操作回顾

| 操作 | 代码位置 | 关键 API |
|------|----------|----------|
| 全量导入 | SearchItemServiceImpl | `solrServer.add(doc)` + `commit()` |
| 增量同步 | ItemAddMessageListener | 同上（单个商品） |
| 查询 | SearchDaoImpl | `solrServer.query(query)` |

### 4.5 搜索质量优化方向（进阶）

- 中文分词器：IK Analyzer（项目未集成，可自学扩展）
- 权重：标题权重高于描述（`boost`）
- 过滤：按价格区间、分类过滤（fq）
- 排序：按销量、价格、新品排序（sort）
- 联想词：suggest 组件

## 5. ActiveMQ 消息中间件

### 5.1 为什么需要消息队列

商品上架后需要做三件事：
1. 写数据库（必须同步，用户要立即看到）
2. 更新 Solr 索引（可以异步）
3. 生成商品静态页（可以异步）

如果 2、3 都同步做，上架接口会变慢、耦合加重。用消息队列把"写库"与"后续处理"解耦：

```
写库成功 → 发一条消息 → 立刻返回"上架成功"
                          │
                          ├→ 搜索服务异步收消息 → 更新索引
                          └→ 静态页服务异步收消息 → 生成 HTML
```

**好处**：
- 响应快（用户无感知等待）
- 解耦（加新消费者不用改主流程代码）
- 削峰（高并发时消息排队，消费者按能力消费）

### 5.2 两种消息模型

| 模型 | 说明 | 本项目用法 |
|------|------|-----------|
| Queue（点对点） | 一条消息只有一个消费者 | `spring-queue`（演示） |
| Topic（发布订阅） | 一条消息所有订阅者都收到 | `item-add-topic`（商品上架通知） |

### 5.3 项目中的生产者（manager-service）

```java
// 注入：主题目的地 + JmsTemplate
@Resource(name = "itemAddTopic")
private Destination destination;

@Autowired
private JmsTemplate jmsTemplate;

// 商品上架成功后发送消息
jmsTemplate.send(destination, new MessageCreator() {
    @Override
    public Message createMessage(Session session) throws JMSException {
        return session.createTextMessage(itemId + "");   // 携带商品ID
    }
});
```

### 5.4 项目中的消费者（search-service / item-web）

```java
public class ItemAddMessageListener implements MessageListener {
    @Override
    public void onMessage(Message message) {
        TextMessage textMessage = (TextMessage) message;
        long itemId = Long.valueOf(textMessage.getText());
        // 1. 重试等待事务提交（最多3次，每次休眠1秒）
        // 2. 查询商品 → 写 Solr 索引（或生成静态页）
    }
}
```

**为什么要重试？** —— 生产者"先写库、再发消息"，但消息到达消费者时，
生产者的数据库事务可能还没提交，此时查询会查不到。用"重试 + 休眠"等待提交完成。

### 5.5 消息可靠性（面试重点）

| 问题 | 对策 |
|------|------|
| 消息丢失 | 持久化 Topic（durable subscriber）；生产端 confirm |
| 重复消费 | 消费者做幂等（本项目未实现，教学可讨论） |
| 消息堆积 | 增加消费者、提高消费能力 |
| 顺序性 | 单队列 + 单消费者（本项目消息无强顺序要求） |

### 5.6 相关配置

`applicationContext-activemq.xml`：

```xml
<!-- 连接工厂 -->
<bean id="targetConnectionFactory" class="org.apache.activemq.ActiveMQConnectionFactory">
    <property name="brokerURL" value="tcp://172.168.20.221:61616"/>
</bean>
<!-- Spring 单连接工厂 -->
<bean id="connectionFactory" class="org.springframework.jms.connection.SingleConnectionFactory">
    <property name="targetConnectionFactory" ref="targetConnectionFactory"/>
</bean>
<!-- 发送模板 -->
<bean id="jmsTemplate" class="org.springframework.jms.core.JmsTemplate">
    <property name="connectionFactory" ref="connectionFactory"/>
</bean>
<!-- 主题 -->
<bean id="itemAddTopic" class="org.apache.activemq.command.ActiveMQTopic">
    <constructor-arg value="item-add-topic"/>
</bean>
```

## 6. FastDFS 分布式文件系统

### 6.1 为什么不用本地磁盘存图片

| 对比 | 本地磁盘 | FastDFS |
|------|----------|---------|
| 容量 | 单机有限 | 可横向扩展（多 Storage） |
| 备份 | 需手动 | 同组内自动互备 |
| 访问 | 依赖应用服务器 | 独立文件服务，与应用解耦 |
| 高可用 | 单点 | Tracker 集群 + Storage 组 |

### 6.2 架构角色

```
┌──────────────┐
│   Tracker    │  调度服务器：管理 Storage，分配上传/下载地址
└──────┬───────┘
       │
┌──────▼───────┐
│  Storage 组  │  存储服务器：group1 下多台 Storage 互为备份
│  group1      │
└──────────────┘
```

- **Tracker**：轻量调度，不存数据
- **Storage**：真正存文件，按组划分（group1、group2…），同组互备
- **文件标识**：`group1/M00/00/01/xxx.jpg`（组名 + 存储路径）

### 6.3 项目中的使用

`FastDFSClient` 封装上传：

```java
// 连接 tracker
ClientGlobal.init(conf);
trackerClient = new TrackerClient();
trackerServer = trackerClient.getConnection();
storageClient = new StorageClient1(trackerServer, storageServer);

// 上传字节数组，返回 group+路径
String result = storageClient.upload_file1(fileContent, extName, metas);
// 完整 URL = IMAGE_SERVER_URL + result
```

`PictureController` 上传图片：
- 校验空文件 → 取扩展名 → 上传 → 拼 URL → 返回 `{"error":0,"url":"..."}`
- `finally` 中 `close()` 释放连接（避免连接泄漏）

### 6.4 上传流程完整链路

```
浏览器选择图片
  → manager-web /pic/upload
  → new FastDFSClient(client.conf) 连接 Tracker
  → Tracker 分配 Storage
  → Storage 写文件，返回 group1/M00/...
  → 拼接 IMAGE_SERVER_URL 返回完整 URL
  → 前端把 URL 填到商品图片字段
```

## 7. MyBatis 与分页

### 7.1 MyBatis 核心概念

| 概念 | 说明 | 项目位置 |
|------|------|----------|
| Mapper 接口 | 定义数据库操作方法 | `taotao-manager-dao/.../mapper/` |
| Mapper XML | SQL 与映射 | 同名 `.xml` |
| POJO | 数据库实体 | `taotao-manager-pojo/.../pojo/` |
| Example | 条件查询对象（MyBatis Generator 生成） | 各 `*Example.java` |

### 7.2 动态 SQL 示例

```xml
<select id="selectByExample" parameterType="com.taotao.pojo.TbItemExample" resultMap="BaseResultMap">
  select
  <if test="distinct">distinct</if>
  <include refid="Base_Column_List"/>
  from tb_item
  <if test="_parameter != null">
    <include refid="Example_Where_Clause"/>
  </if>
  <if test="orderByClause != null">order by ${orderByClause}</if>
</select>
```

### 7.3 PageHelper 分页原理

```java
// 业务代码：分页前调用一次
PageHelper.startPage(page, rows);
// 紧接着的查询自动带上 LIMIT
List<TbItem> list = itemMapper.selectByExample(example);
// 用 PageInfo 取总记录数
PageInfo<TbItem> pageInfo = new PageInfo<>(list);
```

**原理**：PageHelper 是一个 MyBatis **拦截器（Interceptor）**，拦截 SQL 执行，
自动改写为 `LIMIT ?, ?`，并额外执行一条 `SELECT COUNT(*)` 统计总数。

### 7.4 配置

```xml
<bean class="com.github.pagehelper.PageInterceptor">
    <property name="properties">
        <value>
            helperDialect=mysql      <!-- 数据库方言 -->
            reasonable=true          <!-- 页码越界自动纠正 -->
            supportMethodsArguments=true
        </value>
    </property>
</bean>
```

> 注意：`startPage` 只对**紧接着的一条查询**生效，使用后要立即查询，否则分页参数会串到别的 SQL 上。

## 8. Spring 事务管理

### 8.1 声明式事务配置

`applicationContext-trans.xml`：

```xml
<bean id="transactionManager" class="org.springframework.jdbc.datasource.DataSourceTransactionManager">
    <property name="dataSource" ref="dataSource"/>
</bean>

<tx:advice id="txAdvice" transaction-manager="transactionManager">
    <tx:attributes>
        <tx:method name="save*" propagation="REQUIRED" rollback-for="java.lang.Exception"/>
        <tx:method name="insert*" propagation="REQUIRED" rollback-for="java.lang.Exception"/>
        <tx:method name="create*" propagation="REQUIRED" rollback-for="java.lang.Exception"/>
        <tx:method name="update*" propagation="REQUIRED" rollback-for="java.lang.Exception"/>
        <tx:method name="delete*" propagation="REQUIRED" rollback-for="java.lang.Exception"/>
        <tx:method name="select*" propagation="SUPPORTS" read-only="true"/>
        <tx:method name="get*" propagation="SUPPORTS" read-only="true"/>
        <tx:method name="find*" propagation="SUPPORTS" read-only="true"/>
    </tx:attributes>
</tx:advice>

<aop:config>
    <aop:advisor advice-ref="txAdvice"
                 pointcut="execution(* com.taotao.service.*.*(..))"/>
</aop:config>
```

### 8.2 关键点讲解

- **方法命名约定**：`insert*/update*/delete*/create*` 走事务，`select*/get*/find*` 只读
- **rollback-for="java.lang.Exception"**：默认 Spring 只回滚 RuntimeException，这里改为所有异常都回滚
- **propagation="REQUIRED"**：有事务则加入，无则新建（默认行为）
- **AOP 切面**：`execution(* com.taotao.service.*.*(..))` 拦截 service 包下所有方法

### 8.3 典型事务场景：创建订单

`OrderServiceImpl.createOrder` 中：
- 插入订单主表 + 明细表 + 收货表 = 三个写操作
- 任一失败，全部回滚 —— 保证订单数据完整一致

> 注意：`createOrder` 方法名匹配 `create*` 规则，自动纳入事务。

```
└── 工程化：Maven 多模块 + SLF4J + log4j
```
