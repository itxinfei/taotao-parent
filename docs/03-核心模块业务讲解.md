# 03 核心模块业务讲解

> 学习目标：读懂淘淘商城六大核心业务的完整链路 —— 商品、搜索、购物车、订单、单点登录、内容管理。

## 1. 后台管理模块（taotao-manager-web + manager-service）

### 1.1 商品管理 —— 项目的心脏

#### 1.1.1 数据模型

商品信息分布在两张表：

| 表 | 字段要点 | 说明 |
|----|----------|------|
| tb_item | id、title、sell_point、price、num、image、cid、status、created、updated | 商品主表 |
| tb_item_desc | item_id、item_desc、created、updated | 商品描述（富文本 HTML） |

> 为什么拆两张表？—— 描述是长文本（可能几十 KB），列表查询不需要它；拆开能减少主表的行宽，
> 提升列表页查询性能。这是电商表设计的常见手法。

商品状态 `status`：

| 值 | 含义 |
|----|------|
| 1 | 正常（在售） |
| 2 | 下架 |
| 3 | 删除（逻辑删除） |

#### 1.1.2 新增商品完整链路

```
页面 item-add.jsp 提交表单
        │
        ▼
ItemController.addItem(item, desc)
        │  调用 Dubbo 远程服务
        ▼
ItemServiceImpl.createItem()
  1. IDUtils.genItemId() 生成商品ID（时间戳+随机数）
  2. 补全属性：status=1、created、updated
  3. itemMapper.insert(tbItem)           ──► 写 tb_item
  4. insertItemDesc(itemId, desc)         ──► 写 tb_item_desc
  5. jmsTemplate.send(itemAddTopic, itemId) ──► 发消息给搜索/静态化
        │
        ▼
返回 TaotaoResult.ok()
```

**教学重点**：

- **ID 生成**：`IDUtils.genItemId()` 用"13 位毫秒时间戳 + 2 位随机数"拼成 15 位 Long，无需依赖数据库自增，
  适合分布式环境。代码位置：`taotao-common/.../IDUtils.java`
- **消息通知**：新增商品成功后向 `item-add-topic` 主题发消息，携带 itemId。
  搜索服务和静态页服务监听该主题，异步完成"建索引"和"生成静态页"。
  这是典型的**发布-订阅异步解耦**。

#### 1.1.3 商品查询与缓存（重点）

`ItemServiceImpl.getItemById(itemId)` 是理解项目缓存思想的最佳入口：

```java
public TbItem getItemById(long itemId) {
    // 1. 先查 Redis 缓存
    try {
        String json = jedisClient.get(ITEM_INFO + ":" + itemId + ":BASE");
        if (!StringUtils.isBlank(json)) {
            return JSON.parseObject(json, TbItem.class);   // 缓存命中直接返回
        }
    } catch (Exception e) {
        logger.error("查询Redis缓存(商品基础信息)失败", e);
    }
    // 2. 缓存未命中，查数据库
    TbItem tbItem = itemMapper.selectByPrimaryKey(itemId);
    // 3. 回填缓存，并设置过期时间
    try {
        jedisClient.set(ITEM_INFO + ":" + itemId + ":BASE", JSON.toJSONString(tbItem));
        jedisClient.expire(ITEM_INFO + ":" + itemId + ":BASE", ITEM_EXPIRE);
    } catch (Exception e) {
        logger.error("写入Redis缓存(商品基础信息)失败", e);
    }
    return tbItem;
}
```

**缓存设计要点（面试高频）**：

| 设计点 | 本项目做法 |
|--------|-----------|
| Key 设计 | `ITEM_INFO:{itemId}:BASE`（基础信息）/ `:DESC`（描述），按数据类型分区 |
| 过期时间 | `ITEM_EXPIRE=86400` 秒（一天），防缓存无限膨胀 |
| 缓存穿透 | 商品不存在时 `JSON.toJSONString(null)` 也会被缓存为 "null" 字符串（注意这里的隐患与取舍） |
| 缓存一致性 | 更新/删除/上下架商品时 `jedisClient.expire(key, 0)` 立即清除缓存 |
| 容错 | 所有 Redis 操作包 try-catch，Redis 挂了不影响主流程（降级为直查数据库） |

#### 1.1.4 编辑、删除、上下架

| 操作 | 实现要点 |
|------|----------|
| 编辑 updateItem | 更新 tb_item + tb_item_desc；描述不存在则先插入（防丢描述）；清缓存；发 MQ 消息同步搜索 |
| 删除 deleteItem | 逻辑删除：status 置 3，不物理删除；清缓存 |
| 下架 instock | status 置 2 |
| 上架 reshelf | status 置 1 |

> 三个批量操作（删除/上下架）接收逗号分隔的 ID 串，如 `"1,2,3"`，内部遍历并**过滤空 ID**，避免转换异常。

### 1.2 类目管理

- `TbItemCatMapper` 查询 `parent_id = ?` 的子节点
- 返回 `List<EasyUITreeNode>`（id/text/state）给前端 EasyUI 树组件
- `state`：`closed` 表示有子节点（可展开），`open` 表示叶子节点

### 1.3 规格参数管理

| 表 | 作用 |
|----|------|
| tb_item_param | 类目级规格模板（如"手机"类目有哪些参数：品牌、屏幕、电池） |
| tb_item_param_item | 商品级规格实例（某具体手机的品牌=华为、屏幕=6.1英寸） |

`ItemParamItemServiceImpl.getItemParamByItemId` 把 JSON 格式的规格参数动态渲染成 HTML 表格：
把 `[{"group":"主体","params":[{"k":"品牌","v":"华为"}]}]` 解析后拼成 `<table>` 返回给商品详情页。

### 1.4 图片上传（FastDFS）

```
PictureController.picUpload(MultipartFile uploadFile)
  1. 校验空文件、取扩展名
  2. new FastDFSClient("classpath:resource/client.conf")   // 连接 tracker

```

## 2. 搜索模块（taotao-search + taotao-search-web）

### 2.1 Solr 基础概念

| 概念 | 说明 |
|------|------|
| Core（collection） | 一个独立索引库，本项目用 collection1 |
| Document | 一条索引记录，类似表的一行 |
| Field | 字段，类似列；本项目字段：id/title/price/image 等 |
| Schema | 字段定义与类型 |
| 分词器 | 中文分词（IK Analyzer），决定搜索质量 |

### 2.2 索引导入（全量）

入口：后台"索引库管理 → 导入数据"（`IndexManagerController` → `SearchItemServiceImpl.importItemsToIndex`）

```
searchItemMapper.getSearchItemList()   // 从 MySQL 联表查所有在售商品
        │
        ▼
遍历每条数据构造 SolrInputDocument
  id、item_title、item_sell_point、item_price、item_image、
  item_category_name、item_desc
        │
        ▼
solrServer.add(document) → 全部添加后 solrServer.commit()
```

对应 SQL（`SearchItemMapper.xml`）：

```sql
SELECT a.id, a.title, a.sell_point, a.price, a.image,
       b.name AS item_category_name, c.item_desc
FROM tb_item a
LEFT JOIN tb_item_cat b ON a.cid = b.id
LEFT JOIN tb_item_desc c ON a.id = c.item_id
WHERE a.status = 1
```

### 2.3 增量索引（消息驱动）

商品上架时 manager-service 发送 MQ 消息 → search-service 的 `ItemAddMessageListener` 监听：

```
1. 从消息中取出 itemId
2. 最多重试 3 次（每次 sleep 1 秒）查询商品 —— 等数据库事务提交
3. 查到后构造 Document 写入 Solr 并 commit
```

> 为什么重试？消息发送时数据库事务可能还没提交，立刻查会查不到 —— 这是异步场景的经典问题，
> 本项目用"有限重试 + 休眠"简单解决。

### 2.4 搜索查询（重点）

```
SearchController.search(q, page)
  → SearchServiceImpl.search(queryString, page, rows)
     1. 构建 SolrQuery
     2. 分页：setStart((page-1)*rows)、setRows(rows)
     3. 默认搜索域：set("df", "item_title")      // 默认搜标题
     4. 高亮：addHighlightField("item_title")    // 命中词加 <em> 标签
     5. 调 SearchDao.search(query) 执行查询
     6. 计算总页数 totalPages = ceil(recordCount / rows)
  → SearchDaoImpl.search(query)
     1. solrServer.query(query) 得到 QueryResponse
     2. 遍历 SolrDocumentList 组装 SearchItem
     3. 图片取第一张：image.split(",")[0]
     4. 标题优先用高亮结果，否则用原字段
```

**高亮原理**：Solr 在结果中把命中的词用 `<em>手机</em>` 包裹，前端 JSP 直接输出即可显示高亮。

### 2.5 搜索的 JSP 渲染

`search.jsp` 展示：`${itemList}` 循环输出商品卡片（图片、标题（高亮）、价格、卖点），
底部用 `totalPages` 和 `page` 渲染分页条。

## 3. 购物车模块（taotao-cart-web）

### 3.1 购物车为什么有"两套存储"？

| 场景 | 存储 | 原因 |
|------|------|------|
| 未登录用户 | Cookie | 无状态、无需账号，浏览器本地即可 |
| 已登录用户 | Redis Hash | 跨设备同步、服务端可管理 |

**核心思想**：未登录时购物车数据跟着浏览器走（Cookie）；登录后同步到 Redis，
用户换设备也能拿到自己的购物车。

### 3.2 Cookie 购物车

```java
// Key：TT_CART（配置 CART_KEY），Value：购物车商品 JSON 数组
// 读取
List<TbItem> cartItemList = getCartItemList(request);
// 写入（URL 编码 + 设置过期时间）
CookieUtils.setCookie(request, response, CART_KEY,
        JSON.toJSONString(cartItemList), CART_EXPIRE, true);
```

添加商品逻辑（`addItemCart`）：

```
1. 从 Cookie 取出购物车列表
2. 遍历：如果已存在该商品 → num + 本次数量
3. 不存在 → 调 itemService.getItemById 查商品，设置数量，只保留第一张图，加入列表
4. 写回 Cookie
5. 如果已登录，同步到 Redis
```

### 3.3 Redis 购物车（Hash 结构）

```
Key：TT_CART:{userId}
Field：商品ID
Value：商品 JSON
```

```java
// 同步购物车到 Redis
jedis.hset(key, item.getId().toString(), JSON.toJSONString(item));
jedis.expire(key, CART_EXPIRE);

// 展示购物车时合并 Redis 数据（补全 Cookie 中缺失的商品）
List<String> jsonList = jedis.hvals(key);
```

### 3.4 购物车操作汇总

| 接口 | 路径 | 说明 |
|------|------|------|
| 添加 | `/cart/add/{itemId}` | 支持 `?num=2` 指定数量 |
| 展示 | `/cart/cart` | 合并 Cookie + Redis |
| 修改数量 | `/cart/update/num/{itemId}/{num}` | |
| 删除 | `/cart/delete/{itemId}` | Cookie 与 Redis 同时删除 |

## 4. 订单模块（taotao-order + taotao-order-web）

### 4.1 订单数据模型

| 表 | 内容 | 关联 |
|----|------|------|
| tb_order | 订单主表（订单号、金额、状态、买家） | 主键 order_id |
| tb_order_item | 订单商品明细（多行） | order_id |
| tb_order_shipping | 收货地址/物流 | order_id |

> 注意：订单主键 `order_id` 是 **String**，由 Redis 生成 —— 因为订单量大的系统里，
> 数据库自增 ID 在分布式多库下会冲突，且订单号需要业务可读。

### 4.2 订单号生成（Redis incr）

```java
if (!jedisClient.exists(ORDER_ID_GEN_KEY)) {
    jedisClient.set(ORDER_ID_GEN_KEY, ORDER_ID_BEGIN_VALUE);   // 首次设初始值
}
String orderId = jedisClient.incr(ORDER_ID_GEN_KEY).toString(); // 自增
```

**为什么用 Redis incr？** —— `incr` 是原子操作，多线程/多实例并发调用不会重复，
天然适合生成分布式全局唯一自增号。代价是依赖 Redis 可用性（Redis 挂则无法下单，本项目未做降级）。

### 4.3 创建订单完整链路（重点）

```
OrderController.createOrder(orderInfo, model, request, response)
  1. 从 request 取登录用户（LoginInterceptor 放入的 USER_INFO）
  2. 补全 userId、buyerNick
        │
        ▼
OrderServiceImpl.createOrder(orderInfo)
  1. 生成订单号（Redis incr）
  2. 补全订单状态=1(未付款)、创建/更新时间
  3. tbOrderMapper.insert(orderInfo)              // 订单主表
  4. 遍历 orderItems：incr 生成明细ID → 插入 tb_order_item
  5. 插入 tb_order_shipping 收货信息
        │
        ▼
返回 TaotaoResult.ok(orderId)
        │
        ▼
Controller：清空购物车 Cookie → 渲染 success.jsp（订单号、金额、预计3天后送达）
```

### 4.4 订单状态机

| 值 | 状态 | 触发 |
|----|------|------|
| 1 | 未付款 | 下单成功 |
| 2 | 已付款 | （本项目未接入支付，预留） |
| 4 | 已发货 | 后台发货（填物流公司/单号） |
| 6 | 交易关闭 | 超时未支付自动关闭 / 后台手动关闭 |

### 4.5 超时自动关单（Quartz 定时任务）

`OrderJob.execute()` 由 Quartz 每 30 分钟调度一次：

```java
// 扫描：status=1（未付款）且 create_time < 当前时间-2天
example.createCriteria()
    .andStatusEqualTo(1)
    .andCreateTimeLessThan(new Date(System.currentTimeMillis() - 2*24*3600*1000L));

// 逐条置为关闭状态（6）
order.setStatus(6);
order.setCloseTime(new Date());
orderMapper.updateByPrimaryKey(order);
```

配置：`applicationContext-quartz.xml` 中 `cronExpression=0 0/30 * * * ?`（每 30 分钟）。

### 4.6 登录拦截器

`LoginInterceptor` 拦截 `/order/**`：

```
1. URL 带 token 参数？→ 验证 → 写入 Cookie → 重定向去掉 token（处理 SSO 回跳）
2. Cookie 无 token → 跳 SSO 登录页（带上当前 URL 作为回调）
3. token 无效/过期 → 跳登录页
4. 有效 → request.setAttribute("USER_INFO", user) → 放行
```

## 5. 单点登录模块（taotao-sso + taotao-sso-web）

### 5.1 为什么需要 SSO？

淘淘商城有 7 个 Web 模块（门户、搜索、购物车、订单…）。如果每个模块各自实现登录，
用户在一个模块登录后，到另一个模块又要重新登录 —— 体验极差。

**SSO（Single Sign On，单点登录）**：一次登录，处处可用。

### 5.2 登录流程图

```
用户提交用户名/密码（sso-web /user/login）
        │
        ▼
UserServiceImpl.login(username, password)
  1. 按用户名查 tb_user
  2. MD5(password) 与库中比对
  3. 生成 Token：UUID.randomUUID()
  4. 用户信息（去除密码）存 Redis：USER_SESSION:{token}
  5. 设置过期时间 SESSION_EXPIRE
        │
        ▼
返回 TaotaoResult.ok(token)
        │
        ▼
UserController：把 token 写入 Cookie（TOKEN_KEY=TT_TOKEN）
```

### 5.3 其他模块如何验证登录？

```java
// 任意 web 模块：从 Cookie 取 token，调 SSO 服务验证
TaotaoResult result = userService.getUserByToken(token);
if (result.getStatus() == 200) {
    TbUser user = (TbUser) result.getData();   // 验证通过，拿到用户
}
```

**本质**：登录态不再存在各模块自己的 Session 里，而是存在 **Redis**（共享存储）。
任何模块拿到 token 都能去 SSO 换取用户信息 —— 这就是分布式会话共享。

### 5.4 Token 有效期与刷新

| 操作 | 说明 |
|------|------|
| 登录 | 写入 Redis 并设置 `SESSION_EXPIRE`（默认 1 天） |
| 验证 | 每次 `getUserByToken` 都会刷新过期时间（续期） |
| 登出 | `logout`：`expire(token, 0)` 立即失效 |

### 5.5 注册流程

```
UserServiceImpl.register(tbUser)
  1. 校验用户名不能为空、不能重复
  2. 校验密码非空
  3. 手机号/邮箱非空则校验唯一性
  4. 密码 MD5 加密（显式 UTF-8，跨平台一致）
  5. 补全 created/updated → insert
```

> 安全要点：密码只存 MD5 摘要，绝不明文落库；
> 生产环境建议升级为 BCrypt（加盐），本项目为教学保留 MD5。

### 5.6 登录拦截器与跨域

- `LoginInterceptor`（order-web）：拦截需要登录的路径，未登录跳转 SSO 登录页并带回跳 URL
- JSONP 支持：`/user/token/{token}?callback=xxx` 返回 JSONP 格式，解决跨域获取登录态

## 6. 内容管理模块（taotao-content + manager-web 内容页）

### 6.1 用途

门户首页的**广告轮播图**、促销位等内容由运营人员在后台"内容管理"中维护，
通过内容分类（tb_content_category）组织，支持树形结构（父子节点）。

### 6.2 缓存应用

`ContentServiceImpl.getContentListByCid`：

```
1. 查 Redis Hash：hget(INDEX_CONTENT, cid)
2. 命中 → 反序列化返回
3. 未命中 → 查 tb_content 表
4. 回填 Redis：hset(INDEX_CONTENT, cid, json)
```

> Redis Key 用 **Hash 结构**（INDEX_CONTENT → field: 分类ID, value: 内容JSON），
> 一个 Key 管理所有分类的首页内容，便于统一清理。

### 6.3 缓存清理时机

| 操作 | 清理逻辑 |
|------|----------|
| 新增内容 | `hdel(INDEX_CONTENT, categoryId)` |
| 编辑内容 | 先查旧内容拿旧分类ID，删旧分类缓存；若分类变更，新分类缓存也要清理 |
| 删除内容 | 查内容拿分类ID → 删缓存 → 删记录 |

> 注意：清理缓存操作全部 try-catch 容错 —— Redis 挂了不影响数据库主流程（与商品缓存同一思想）。

### 6.4 内容分类的树操作

| 操作 | 要点 |
|------|------|
| 新增分类 | 插入后，若父节点是叶子则置 is_parent=true |
| 删除分类 | 逻辑删除（status=2）；递归删除子节点；父节点无活跃子节点则置回叶子 |

## 7. 门户与商品详情

### 7.1 门户首页（taotao-portal-web）

```
IndexController.showIndex(model)
  1. contentService.getContentListByCid(AD1_CATEGORY_ID)  // 拉广告位内容
  2. 组装 AD1Node（宽高、图片、链接）
  3. JSON 序列化后放入 model "ad1"
  4. index.jsp 用 JS 渲染轮播图
```

### 7.2 商品详情页（taotao-item-web）

```
ItemController.showItem(itemId, model)
  1. itemService.getItemById(itemId)      // 基础信息（带 Redis 缓存）
  2. itemService.getItemDescById(itemId)  // 描述（带 Redis 缓存）
  3. 包装成 Item 对象（附加 getImages() 拆图方法）
  4. item.jsp 渲染：图片、价格、标题、描述
```

### 7.3 FreeMarker 页面静态化

商品详情页是访问量最大的页面之一，动态渲染每次都要查库。
项目用 FreeMarker 把详情页**生成静态 HTML**：

```
ItemAddMessageListener（item-web 监听 MQ）
  1. 收到 itemId
  2. 查询商品 + 描述
  3. 用 item.ftl 模板 + 数据 → 输出到 HTML_OUT_PATH/{itemId}.html
  4. Nginx/静态服务器直接返回静态页，扛住高并发
```

> 动静分离思想：动态接口（查询）与静态页面（渲染）分离，静态页由 CDN/静态服务器加速。
