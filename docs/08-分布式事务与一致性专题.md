# 08 分布式事务与一致性专题

> 学习目标：理解分布式环境下"数据一致性"为什么难，掌握本地消息表、事务消息、TCC、最终一致性等
> 主流方案的原理与适用场景，并能结合淘淘商城讲清楚"商品上架 → 建索引"这个真实的一致性问题。

---

## 1. 为什么需要分布式事务

### 1.1 单体 vs 分布式

| 场景 | 单体应用 | 分布式应用（本项目） |
|------|----------|---------------------|
| 商品上架 | 写库 + 建索引在一个进程一个事务 | 写库（manager-service）+ 建索引（search-service）跨两个进程 |
| 下单 | 扣库存 + 写订单在一个事务 | 写订单（order-service）+ 减库存（可能在不同服务） |
| 事务保证 | 数据库本地事务 ACID | 跨库/跨服务无法用本地事务 |

**核心矛盾**：本地事务只对"同一个数据库连接"有效；分布式场景下，一个业务操作分散在多个服务、多个库，
无法用单库事务保证原子性。

### 1.2 本项目的一致性问题实例

**商品上架链路**：

```
manager-service.createItem()
  1. 写 tb_item（MySQL）        ← 本地事务 A
  2. 发消息到 item-add-topic    ← 跨进程操作 B
        │
        ▼
search-service 监听消息 → 写 Solr 索引   ← 跨进程操作 C
```

**潜在不一致**：
- 步骤 1 成功、步骤 2 失败 → 商品入库了但索引没同步（搜索不到）
- 步骤 1 成功、步骤 2 成功但 C 消费失败 → 同上
- 步骤 2 成功但步骤 1 回滚 → 索引里有"幽灵商品"

## 2. 一致性基础理论

### 2.1 CAP 定理

分布式系统无法同时满足以下三者：

| 字母 | 含义 | 说明 |
|------|------|------|
| C | Consistency 一致性 | 所有节点同一时刻看到同一数据 |
| A | Availability 可用性 | 请求总能得到响应 |
| P | Partition tolerance 分区容错 | 网络分区时系统仍工作 |

**结论**：网络分区不可避免（P 必选），只能在 C 和 A 之间取舍。

- **CP**：ZooKeeper、etcd（牺牲部分可用性保证强一致）
- **AP**：Eureka、Cassandra（允许短暂不一致，最终一致）

**项目结合**：本项目用 ZooKeeper 做注册中心（CP），Dubbo 服务发现偶尔失败会重试（可接受短暂不一致）。

### 2.2 BASE 理论

| 字母 | 含义 |
|------|------|
| BA | Basically Available 基本可用 |
| S | Soft state 软状态（允许中间态） |
| E | Eventually consistent 最终一致 |

**核心思想**：不追求强一致，允许短暂不一致，最终通过补偿/重试达到一致。

**项目结合**：商品上架后"索引同步、页面静态化"都是异步的，就是 BASE 思想的体现 —— 用户看到商品上架成功，
索引在 1~3 秒内同步，属于**最终一致**。

### 2.3 强一致 vs 最终一致

| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
|------|--------|------|--------|------|
| 2PC/XA | 强一致 | 低 | 高 | 银行转账等 |
| TCC | 较强 | 中 | 高 | 资金类、需回滚 |
| 本地消息表 | 最终一致 | 高 | 中 | 通用异步场景 |
| 事务消息（RocketMQ） | 最终一致 | 高 | 中 | 通用异步场景 |
| MQ 消息 + 重试 | 最终一致 | 最高 | 低 | 容忍失败重试的场景 |

## 3. 主流分布式事务方案详解

### 3.1 方案一：2PC / XA（两阶段提交）

**原理**：

```
阶段一（准备）：协调者询问所有参与者"能提交吗？"，参与者锁定资源并返回 OK/失败
阶段二（提交）：全部 OK → 协调者让所有参与者提交；任一失败 → 全部回滚
```

**优点**：强一致
**缺点**：
- 同步阻塞：准备阶段锁资源，性能差
- 协调者单点故障
- 数据不一致风险（提交阶段网络故障）

**适用**：对一致性要求极高的场景；本项目未使用（性能不可接受）。

### 3.2 方案二：TCC（Try-Confirm-Cancel）

**原理**：把业务拆成三个操作：

| 阶段 | 操作 | 示例（下单扣款） |
|------|------|------------------|
| Try | 预留资源 | 冻结金额、预占库存 |
| Confirm | 确认执行 | 真正扣款、扣库存 |
| Cancel | 取消回滚 | 释放冻结资源 |

**优点**：业务级控制，比 2PC 灵活，非阻塞
**缺点**：
- 侵入性强：每个业务要写三套逻辑
- 空回滚、悬挂、幂等等问题需要处理

**适用**：金融、支付、跨服务资金流转。

### 3.3 方案三：本地消息表（本项目可落地）

**原理**：

```
业务服务本地事务：
  1. 写业务表（如 tb_item）
  2. 同时写一张"消息表"（如 tb_msg，状态=待发送）
  3. 本地事务提交（两步同库，保证原子）
之后：
  4. 定时任务扫描消息表，发送 MQ
  5. 消费者处理成功 → 回调更新消息状态=已发送
  6. 发送失败 → 重试；多次失败 → 人工/死信处理
```

**优点**：最终一致、实现简单、不依赖特殊中间件
**缺点**：消息表和业务表耦合；需额外定时任务

**落地示例（伪代码）**：

```java
@Transactional
public TaotaoResult createItem(TbItem tbItem, String desc) {
    // 1. 写商品（业务表）
    itemMapper.insert(tbItem);
    // 2. 写本地消息表（同事务）
    TbMsg msg = new TbMsg();
    msg.setContent(itemId + "");
    msg.setStatus(0);  // 0-待发送
    msgMapper.insert(msg);
    return TaotaoResult.ok();
}
```

```java
// 定时任务：扫描待发送消息 → 发 MQ → 标记已发送
public void scanAndSend() {
    List<TbMsg> list = msgMapper.selectByStatus(0);
    for (TbMsg msg : list) {
        try {
            jmsTemplate.send(destination, msg.getContent());
            msg.setStatus(1);
            msgMapper.updateByPrimaryKey(msg);
        } catch (Exception e) {
            logger.error("发送失败，等待重试", e);  // 下次扫描重试
        }
    }
}
```

### 3.4 方案四：事务消息（RocketMQ）

**原理**：RocketMQ 提供的半消息机制：

```
1. 发送"半消息"（消费者不可见）
2. 本地事务执行
3. 本地事务成功 → commit 半消息（消费者可见）；失败 → rollback
4. 长时间未确认 → Broker 回查本地事务状态
```

**优点**：消息与业务解耦、无需消息表
**缺点**：依赖 RocketMQ（本项目用 ActiveMQ，无法直接用）

### 3.5 方案五：MQ 消息 + 重试（本项目现状）

本项目现状：

```
createItem 写库成功 → jmsTemplate.send() 发消息
```

问题：发消息与写库不在同一事务，可能"写库成功但发消息失败"。

**教学改进建议**（低成本增强）：

```
方式 A（推荐教学）：写库后同步发消息 + 失败重试 3 次 + 最终人工补偿
方式 B：本地消息表（见 3.3），彻底解决
```

## 4. 本项目的三个一致性场景分析

### 4.1 场景一：商品上架 → 搜索索引同步

| 现状 | 风险 | 改进建议 |
|------|------|----------|
| 写库成功 → 直接发 MQ | 发消息失败则索引缺失 | 本地消息表 / 事务消息 |
| 消费者查不到商品（事务未提交） | 空查询 | 已用"3 次重试 + 休眠 1 秒"缓解 |
| 消费者处理失败 | 索引缺失 | 记录失败日志 + 定时补偿 |

### 4.2 场景二：商品上架 → 静态页生成（item-web）

与场景一同构：写库 → 发消息 → 生成 HTML。
风险：消息丢失则静态页不更新 → 用户看到旧页面。
改进：静态页带版本号/时间戳，定时全量重建兜底。

### 4.3 场景三：下单 → 扣库存（扩展讨论）

本项目未实现扣库存联动，面试可延伸：

```
方案 A：下单事务内 update tb_item set num=num-? where id=? and num>=?
        （乐观锁，更新行数为 0 说明库存不足）
方案 B：Redis 预扣 + 异步落库
方案 C：MQ 异步扣库存 + 本地消息表
```

**防超卖核心**：`UPDATE ... SET num = num - #{n} WHERE id = #{id} AND num >= #{n}`
—— 利用数据库行锁 + 条件更新保证不超卖（比先查后更安全）。

## 5. 面试高频题

### Q1：什么是最终一致性？和强一致的区别？

强一致：任何时刻读到的都是最新值（2PC）。
最终一致：允许中间不一致，经过一段时间（重试/补偿）后达到一致（本地消息表、MQ 重试）。

### Q2：你的项目里哪里用了分布式事务？

诚实回答：
- "本项目主要通过 **ActiveMQ 异步消息 + 消费者重试** 实现最终一致（商品上架 → 索引同步）"
- "严格来说没有用 2PC/TCC；如果需要强一致，我会用本地消息表或 RocketMQ 事务消息"

> 加分点：主动指出当前方案不足，并给出改进方案 —— 面试官最喜欢看到"知道边界、能自我迭代"。

### Q3：本地消息表和事务消息的区别？

| 对比 | 本地消息表 | 事务消息 |
|------|-----------|----------|
| 实现 | 业务库加消息表 + 定时任务 | MQ 半消息 + 回查 |
| 耦合 | 消息表与业务库耦合 | 解耦 |
| 依赖 | 任意 MQ | 需 RocketMQ |
| 复杂度 | 中 | 中 |

### Q4：TCC 的 Try 阶段为什么要"预留"而不是直接扣？

预留是为了 Confirm 阶段一定能成功 —— 把"可能失败的扣减"提前到 Try 阶段做（检查+冻结），
Confirm 只做"确定会成功"的提交，从而避免分布式事务的回滚问题。

### Q5：消息重复消费怎么办？（幂等）

1. 消费前查唯一键：`SELECT 1 FROM tb_x WHERE biz_id=?` 已存在则跳过
2. Redis setnx 做去重标记
3. 让操作本身幂等：更新型操作天然幂等；插入型用唯一索引兜底

**项目结合**：搜索消费者重复消费同一条消息 → 重复 add 相同 id 的文档到 Solr（Solr 按 id 覆盖，天然幂等，问题不大）。

## 6. 一致性实战建议（给学员）

### 6.1 本项目的落地改造（按成本从低到高）

| 成本 | 改造 | 效果 |
|------|------|------|
| 低 | 发消息失败重试 3 次 + 记录失败日志 | 减少消息丢失 |
| 低 | 消费者失败消息写入"重试表"，定时重发 | 自愈 |
| 中 | 本地消息表（3.3 方案） | 彻底解决"写库成功但消息丢失" |
| 高 | 引入 RocketMQ 事务消息 | 标准方案，无需消息表 |

### 6.2 通用一致性检查清单

1. 每个跨服务写操作：是否有补偿/重试机制？
2. 消息失败：是否记录日志可追溯？
3. 消费是否幂等？
4. 是否需要本地消息表？
